# Personal Life OS · Cloud Edition

Public program only. Never commit personal settings, backups, health records, tokens or private data here. Upload files in this folder to a public repository root; enable Pages from main / root. HTTPS is required for PWA install.

Personal data stays in browser storage or a dedicated private GitHub repository. Only grant a fine-grained token for that private repository, Contents read/write. Never publish the private repository or turn on Pages there. Git history may retain old records. No remote images or third-party JavaScript.

## V4.0.2: encrypted device authorization

Configure each device/browser separately with its own GitHub token and an independent unlock passphrase (at least 12 characters; prefer a long unique phrase). The token is encrypted with AES-256-GCM and a random 96-bit nonce. A non-exportable key is derived using PBKDF2-SHA-256 (600,000 iterations, random 128-bit salt). The repository name and vault version are authenticated with the ciphertext. Only the encrypted envelope and derivation parameters are stored in IndexedDB. Neither the passphrase nor the derived key is persisted. The token and passphrase are not part of life-data exports, reports, or GitHub synchronization.

Reload/reopen starts locked. Unlock once, then changes synchronize while the app is open, on returning to the foreground, and when connectivity returns. This does not provide reliable closed-app/background synchronization on iPhone. Manual locking clears the in-memory credential and aborts pending requests; a write already accepted by GitHub cannot be recalled. HTTP 401 locks the credential and asks for a replacement token. Clearing this browser's saved authorization does not delete life records or revoke the token at GitHub. Close other unlocked windows as well; revoke a lost device's token in GitHub settings.

This is a browser vault, not an OS keychain or biometric login. It protects stored tokens from plaintext exposure, subject to passphrase strength. It does not encrypt life records already stored in localStorage or protect against malicious same-origin scripts capturing an unlock passphrase/token. GitHub Pages projects under the same hostname share an origin. Use only trusted code on that origin; a dedicated origin/profile reduces exposure. Browser data clearing/eviction can remove the vault, requiring token setup again. If the passphrase is forgotten, clear the local authorization and configure a token again; life records remain intact.

Verification: real WebCrypto round trips and tamper/wrong-passphrase rejection; simulated IndexedDB transaction failure, fresh-context unlock, credential expiry, offline recovery, and lock during sync; 12 simulated view renders. Physical Safari/iPhone and Edge/PWA behavior still require device acceptance testing.

Existing V4 backups are importable; import replaces local state. Back up first. New fields can be entered in Settings > 私人配置.

## V4.0.3: Beijing application time

The app uses Beijing time (UTC+08:00) for today, posture timestamps, daily totals, manual entry and sync status on every device. OS time zones remain unchanged. Both devices need this version for consistent date views. Calendar arithmetic does not depend on the host time zone.

Historical posture records with valid timestamps are projected onto Beijing calendar days without rewriting their stored dates, timestamps or durations. A record crossing Beijing midnight contributes only its corresponding duration to each day; editing or deleting it affects the complete original record. Records without usable timestamps and existing date-only diary entries retain their original dates. Dates before the plan start remain accessible. New live sessions split at Beijing midnight. Tokens, encrypted vaults and private-data formats are unchanged.

Verification includes the same app running under simulated Pacific and Shanghai host time zones, midnight splitting and duration conservation, manual-entry parsing, and unchanged historical source records. Physical two-device acceptance remains a separate step.

## V4.0.4: private review reports

The Reports tab reads daily, weekly and monthly reviews from the same private data repository with the existing unlocked device authorization. Report reads never write to lifeos-data.json or merge reports into life-data backups. Reports are generated by the separately configured cloud tasks; GitHub Pages contains the viewer only, never private reports. The viewer checks that the repository remains private with Pages disabled before fetching reports.

Paths are reports/daily/YYYY-MM-DD.json (analysis day), reports/weekly/YYYY-MM-DD.json (review ending day), and reports/monthly/YYYY-MM.json (previous complete month). Each task updates only its own period file using the current GitHub content SHA, retries bounded conflicts after re-reading, and verifies the saved content. Changes must not overwrite concurrent life records or other report files.

JSON schema version 1 requires: schemaVersion=1; type=daily|weekly|monthly; periodKey matching its filename; timezone=Asia/Shanghai; title (1–160 characters); generatedAt, periodStart, periodEnd (ISO timestamps with explicit UTC offset, start inclusive/end exclusive); source.repository matching the private repository; source.dataSha and source.principlesSha (40-character lowercase blob SHAs from actual source reads); markdown (1–60,000 characters). No credentials. JSON is encoded as UTF-8.

The viewer uses a complete recursive Git tree to discover reports and retrieves immutable blobs by SHA. It rejects truncated listings and malformed documents. Markdown headings, paragraphs, bold text and simple lists are displayed; raw HTML, links and images are rendered as text and never loaded. This avoids running report-supplied scripts or requesting third-party resources.

Opening Reports, refreshing manually, or successful automatic life-data sync while Reports is open checks the report list. Previously opened reports are cached separately per repository for offline viewing (up to ten per category plus the selected report). Cached report content is not encrypted, consistent with local life records; locking clears authorization and aborts pending reads, but does not hide offline records. Failed downloads preserve valid cached reports and label stale versions. Nothing syncs reliably while the iPhone app is fully closed; reopen and unlock to fetch new reports.

Validation: simulated private GitHub tree/blob reads, three categories, updated SHA reads, offline cache, repository isolation, malformed/unsafe Markdown, truncated listing, lock during requests, existing encrypted authorization and data-merge tests. Physical iPhone acceptance remains required; browser automation was unavailable due host path configuration.
